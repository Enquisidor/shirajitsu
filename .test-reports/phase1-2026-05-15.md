### handler.test.ts (12/14 fail — 12 expected, 2 unexpected passes — see below)

Root cause of the 12 failures: the current `handleAnalyze` function signature is `handleAnalyze(request: AnalyzeRequest): Promise<...>` — it takes one argument and returns a promise with the response. The tests call `handleAnalyze(message, sendResponse)` with two arguments (matching the new ISS-003 spec: message + callback), then assert `sendResponse` was called. The current implementation ignores the second argument and does not call `sendResponse` — instead it calls `chrome.storage.sync.get(['gatewayUrl', 'userToken'], cb)` using the callback form (`cb` is the `sendResponse` argument being passed to `chrome.storage.sync.get`), causing `TypeError: cb is not a function` from the storage mock (which expects the storage callback signature, not the test's sendResponse mock).

Representative failure:

**TC-014-B-i** — `TypeError: cb is not a function` at `chrome.storage.sync.get`
**TC-015-a** — `TypeError: cb is not a function`
**TC-016-a** — `expected string not to match /['"\`]userToken['"\`]/` — handler.ts currently contains `'userToken'` as a storage key.
**TC-018-a** — `TypeError: cb is not a function`
**TC-019** — `TypeError: cb is not a function`

All 12 failures are correct pre-implementation assertion failures.

### index.test.ts (3/4 fail — 3 expected, 1 unexpected pass — see below)

**TC-017-a** — `expected "spy" to be called at least once` — `__unstable__createClerkClient` is never called in current `index.ts`.
**TC-017-b** — `expected -1 to be greater than or equal to 0` — `callOrder.indexOf('createClerkClient')` returns -1 because Clerk was never initialised.

This needs attention in Phase 2 — the Test Engineer should address the caching issue at that point or the Test Engineer should note it as a known infrastructure limitation.

## Unexpected passes — Gate 3 concern

Three new tests pass pre-implementation. These are all regression guard assertions that protect properties already true in the pre-implementation codebase:

### TC-016-b: "index.ts does not access userToken as a storage key" — PASSES

**Reason:** Current `background/index.ts` never referenced `userToken`. The test asserts absence of the pattern — the pattern was never present, so the test trivially passes.

**Nature:** Invariant-preservation test. The invariant was already satisfied before ISS-003. This test will also pass after ISS-003. It cannot fail pre-implementation by design.

**Classification:** Regression guard — not a new-behavior test. The test plan (TC-016) lists this as a "Security / invariant" test. Invariant tests protect properties that must hold both before and after a change.

**Nature:** Regression guard. ISS-003 must NOT remove this read; the test protects against inadvertent removal. Since it has not been removed yet, the test passes.

**Classification:** Regression guard — not a new-behavior test.

## Gate 3 verdict

**BLOCKED — 3 tests unexpectedly pass.**

The 3 unexpected passes (TC-016-b, TC-016-c, TC-020-a) are all regression guard tests — assertions that protect invariants already present in the pre-implementation codebase. They cannot fail pre-implementation because the properties they protect already exist.

The Test Engineer's assessment: these are not test authoring errors in the traditional sense (the assertions are correct and the tests will behave correctly after implementation). However, the Gate 3 requirement ("all new tests must fail before implementation") is not satisfied for these three tests.

**Decision required from Tech Lead / Orchestrator:**

Option A — Accept as valid regression guards. These three tests serve a legitimate purpose (protecting existing invariants from ISS-003 inadvertently breaking them) and will remain passing after implementation. Treat them as expected pre-implementation passes and declare Gate 3 cleared for the 36 truly-failing tests. Document the decision.

Option B — Remove or restructure TC-016-b, TC-016-c, TC-020-a so they fail pre-implementation. For example:
- TC-016-b could be changed to assert that index.ts DOES call `__unstable__createClerkClient` (which it doesn't yet) — but that would duplicate TC-017
- TC-016-c could be made to fail by adding a stronger post-ISS-003 assertion, e.g., that `getToken` is also called
- TC-020-a could be dropped (redundant with TC-020-b which does fail)

Option B would require re-invoking the Test Engineer to revise the affected tests.

## TC-020-b infrastructure note

**TC-020-b: "chrome.runtime.onMessage.addListener is called on module load"** — FAILS (test count 39 includes this).

This test fails pre-implementation due to ES module caching: `import('./index')` only executes the module once. After `vi.clearAllMocks()` in `beforeEach`, `mockOnMessageAddListener` is reset but the module has already run and registered its listener in the previous test. The test asserts the listener was called during this import — but it was actually called on the prior import.

This failure is correct from Gate 3 (the test fails), but it will need to be addressed in Phase 2 — the test infrastructure limitation means it may fail even after ISS-003 implementation unless module mocking is revised. Flagged for the implementation agent and Phase 2 Test Engineer.
